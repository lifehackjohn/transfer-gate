1. Architecture Overview

Transfer Gate v2 is a three-component system designed for portable file sorting across online and air-gapped zones:

  1. transfer-gate.html — Single-file portable UI (HTML + CSS + JS). Runs in any modern browser. Detects environment and switches between online and offline modes.
  2. transfer-gate-server.py — Python 3 HTTP backend for the online zone. Provides filesystem access, oMLX AI classification, batch staging, and config management.
  3. transfer-gate.ps1 — PowerShell engine for the offline zone. Handles verification, file placement, structure export, and can serve the HTML UI locally.

The central abstraction is the Cabinet — a root folder (e.g., D:\Archive) containing a hierarchical tree of subfolders that serves as both the filing taxonomy and the physical storage.

2. Cabinet Abstraction

What is the Cabinet?

The Cabinet is the root folder of the user's hierarchical file archive. It contains numbered top-level folders (e.g., “10 Finance”, “20 Legal”) with nested subfolders. The folder hierarchy IS the classification taxonomy.

Path Resolution Chain

When the app starts, it resolves the Cabinet path through this chain:

  1. Config file — transfer-gate.json: cabinetRoot
  2. Validation — does the path exist and is it accessible?
  3. Interactive fallback — prompt user via settings overlay
  4. Session storage — remember for current session

Mount Variant Handling

ScenariocabinetRoot valueNotes
Windows local driveD:\ArchiveMost common offline setup
Windows UNC\\NAS\share\ArchiveNetwork share
Linux/macOS mount/volume1/ArchiveNAS or mounted drive
WSL path/mnt/d/ArchiveWindows Subsystem for Linux
Portable (relative)./CabinetRelative to app directory

oMLX Folder Understanding

The AI classification uses the Cabinet's folder tree as its taxonomy. The full folder hierarchy (from structure-rules.yaml or live scan) is included in the classification prompt. The AI returns a suggested folder path and confidence score. Folder descriptions from structure-rules.yaml enrich the prompt.

Structure Rules

Defined in structure-rules.yaml and editable via the UI. They add metadata (descriptions, accepted file types, naming conventions) to folders but do not replace the folder hierarchy as the primary taxonomy.

3. Component Design

transfer-gate.html

  • Environment detection: on load, attempts to reach /api/health. If reachable, enters online mode. If not, enters offline mode (localStorage-based).
  • Online mode: full sort-and-stage workflow with AI classification.
  • Offline mode: verify-and-place workflow, or serves as viewer for manifests.
  • Tech: vanilla HTML/CSS/JS, no frameworks, no build step, no CDN.

transfer-gate-server.py — Endpoints

EndpointMethodDescription
/api/healthGETServer health check, returns version
/api/filesGETList unsorted files in tosort/ directory
/api/cabinetGETLoad Cabinet folder tree
/api/classifyPOSTClassify a file using oMLX
/api/stagePOSTStage accepted files into a batch
/api/configGET/PUTRead or update configuration
/api/structure-rulesGET/PUTRead or update structure-rules.yaml
/GETServe transfer-gate.html

oMLX Classification Strategy

  1. Build prompt with file metadata (name, extension, size, date) and full Cabinet tree with descriptions.
  2. Send to local oMLX endpoint (OpenAI-compatible chat API).
  3. Parse response for suggested folder path and confidence (0.0–1.0).
  4. If oMLX is unreachable, return empty suggestion (UI shows manual-only mode).

transfer-gate.ps1 — Modes

ModeDescriptionKey Operations
serveStart local HTTP server for HTML UIBind localhost:8080, serve HTML, handle API calls
verifyVerify inbound USB batchesCheck existence, size, SHA-256 per transfer-manifest
placeMove verified files to CabinetRead placement-manifest, handle conflicts, move files
exportExport Cabinet structureWalk tree, emit offline-structure-manifest.json
allRun verify then export (default)Combined workflow

Config: reads transfer-gate.json from script directory. Auto-migrates v1 format (archiveRoot to cabinetRoot).

4. Data Flow

Full round-trip data flow through all four phases:

Phase 1: Online Sort & Stage

  1. User opens browser to localhost:8080
  2. Server loads unsorted files from tosort/
  3. Server loads Cabinet tree (live or from manifest)
  4. AI classifies each file, suggests destination
  5. User reviews, accepts/overrides, renames files
  6. User clicks “Stage Batch”
  7. Server creates batch-YYYYMMDD-HHMMSS/ with payload/ and manifests

Phase 2: USB Transfer

  1. User copies batch folder to USB stick
  2. User carries USB to offline machine
  3. USB plugged into offline workstation

Phase 3: Offline Verify & Place

  1. User opens Transfer Gate on offline machine
  2. App detects offline mode
  3. User selects batch from inbox
  4. PowerShell verifies every file (SHA-256)
  5. UI shows placement preview
  6. User clicks “Place Files”
  7. PowerShell moves files to Cabinet destinations
  8. Placement receipt generated

Phase 4: Return Trip

  1. User copies placement-receipt.json to USB
  2. Optionally exports updated structure manifest
  3. Returns USB to online machine
  4. Online side reads receipt, marks source files as safe to prune

6. Partial Structure Mirror

The online zone does not need the full Cabinet — only its folder structure. The offline export produces offline-structure-manifest.json containing directory paths and aggregate counts (file count, total bytes per folder). No individual filenames or file contents cross the gate. This sparse tree approach keeps the USB payload small and avoids leaking file inventories.

8. Security

  • Metadata only for oMLX: file contents are never sent to the AI. Only filename, extension, size, and date are included in classification prompts.
  • Localhost binding: both Python and PowerShell servers bind to 127.0.0.1 only, rejecting connections from other machines.
  • SHA-256 checksums: every file in every batch has a checksum computed at staging and verified at placement. Mismatch = verification failure.
  • No credentials stored: no API keys, no tokens, no passwords in config or manifests.

10. Migration from v1

  • v1 manifests (transfer-manifest.json) are recognized and processed by both Python and PowerShell components.
  • v1 config (archiveRoot key, absolute inbox paths) is auto-migrated to v2 format (cabinetRoot key, relative paths) on first load.
  • v1 PowerShell scripts (if present) are not modified but are superseded by transfer-gate.ps1 modes.
  • Migration is automatic and non-destructive — v1 config keys are preserved alongside v2 keys.
