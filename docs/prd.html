PRD — Transfer Gate v2

Portable Online/Offline File Sorting App

Status: Rev 4 — First-run zero-config + offline world clarity
Issue: BLU-2656 (design) / BLU-2674–2678 (path UI, portable Python, offline launch)
Product repo: github.com/lifehackjohn/transfer-gate

1. Problem Statement

The household digital archive spans two separate worlds that never share a live network:

WorldMachineRoleRuntime
Online Mac Mini / NAS-mounted paths (or any online workstation) Unsorted intake (source), AI-assisted classify/rename, stage batches to a transfer folder transfer-gate-server.py + browser UI; optional oMLX
Offline Air-gapped Windows PC + large NTFS Cabinet volume Receive USB/batch, verify checksums, place into Cabinet tree, export structure/receipts back transfer-gate.ps1 -Mode serve (or CLI modes) + same transfer-gate.html

The only bridge is physical media (USB) carrying batch folders + manifests. There is no live mount of the Cabinet from the online world.

First-run rule (board): the app and servers MUST start with empty path settings. Source, sorted/outbox, and Cabinet are configured later in Settings (or by editing transfer-gate.json). A missing directory MUST NOT prevent the UI or HTTP server from launching.

2. Goals

IDGoal
G-1Reduce per-file sorting effort to under 30 seconds with AI-assisted classification.
G-2Provide a portable UI that works in both online (NAS + Python) and offline (air-gapped Windows + PowerShell) zones with the same HTML file.
G-3Guarantee safe data movement — no file is deleted from the source until a verified receipt returns through the gate.
G-4Minimize the online footprint — metadata and manifests only; bulk files stay on the Cabinet drive.
G-5Enable one-click batch staging and one-click batch placement.
G-6Make the Cabinet mount-agnostic — a single config value (cabinetRoot) controls where the Cabinet is expected; changing the drive letter or mount point requires only a config update.
G-7Use folder names as taxonomy — the hierarchical folder structure of the Cabinet IS the classification system; structure-rules.yaml adds metadata and constraints but folders are primary.

3. User Stories

US-0: Zero-config first launch + path setup

As a user, I double-click a launcher and the app opens immediately with empty paths. A clear Setup banner lists missing Source / Sorted / Cabinet. I set them in Settings (or JSON) when ready; the app adapts without reinstall. Servers never refuse to start solely because a path is empty.

Online world

IDStory
US-1As a user, once Source is configured, I see unsorted files from that folder in the left panel with metadata (name, size, date, extension).
US-2As a user, I see an AI-suggested destination folder and confidence score for each file, powered by a local oMLX model.
US-3As a user, I can accept, override, or skip the AI suggestion for each file using the file card controls.
US-4As a user, I must provide a renamed filename following the naming convention before a file can be staged (mandatory rename).
US-5As a user, I click “Stage Batch” and all accepted files are copied into a timestamped batch folder with a placement-manifest.json.

Offline world (air-gapped Windows + Cabinet)

Offline is not “open the HTML file and hope.” It is a full second runtime:

  • Launcher: Start-TransferGate.bat starts PowerShell transfer-gate.ps1 -Mode serve and opens the browser (no Python required).
  • Same UI: transfer-gate.html talks to the PS1 HTTP server on localhost (or falls back if nothing listens).
  • Cabinet: large NTFS archive (e.g. D:\Archive) configured only on this machine — drive letter may differ from any online path.
  • Work: drop USB batch into inbox → verify SHA-256 → placement preview → place into Cabinet → write receipts → optionally export structure for the online AI.
  • CLI modes (no UI): verify, place, export, all — these require a configured Cabinet; serve does not require it at start.
IDStory
US-6As a user, I start Transfer Gate offline with the Windows offline launcher; UI loads even if Cabinet path is not set yet.
US-7As a user, after setting Cabinet (and pointing at an inbound batch), I see verification status (checksum pass/fail) for every file.
US-8As a user, I see a placement preview showing where each file will land in the Cabinet tree.
US-9As a user, I click “Place Files” and all verified files are moved to their Cabinet destinations, with conflict handling.
US-9bAs a user on Windows online (not air-gapped), I can run the Python path via Start-TransferGate-Online.bat with system Python or portable embed download — distinct from the offline PowerShell launcher.

Cross-Zone

IDStory
US-10As a user, I carry a USB stick from the online machine to the offline machine and back, and the manifests handle the full round trip.
US-11As a user, I can export the Cabinet folder structure from the offline machine so the online AI has an up-to-date target tree.
US-12As a user, returning the USB with placement receipts allows the online side to safely prune staged files.

4. Functional Requirements

Core Architecture

IDRequirement
FR-1The app SHALL consist of a single HTML file (transfer-gate.html) that works in both zones.
FR-2The HTML UI SHALL detect whether a Python backend is available and switch between online and offline modes automatically.
FR-3Online mode SHALL use a Python 3 HTTP server (transfer-gate-server.py) for filesystem access and oMLX communication.
FR-4Offline mode SHALL use a PowerShell HTTP server (transfer-gate.ps1 -Mode serve) or run as a static file with localStorage fallback.

Configuration & Cabinet

IDRequirement
FR-5Three paths SHALL be independently configurable: sourcePath (unsorted intake), sortedPath (batch outbox / transfer staging), cabinetRoot (archive). Editable in Settings and transfer-gate.json.
FR-5aZero-config start: Python and PowerShell serve SHALL start successfully when any or all of those paths are empty. Missing paths SHALL surface as UI Setup guidance, not process exit codes that kill the launcher.
FR-5bOperations that need a path (scan source, stage batch, place into Cabinet, verify against Cabinet) SHALL fail that operation with a clear message if the path is unset — without preventing the rest of the app from running.
FR-6The Cabinet tree SHALL be loaded from the live filesystem when cabinetRoot is set, or from offline-structure-manifest.json when used as taxonomy fallback online.
FR-7Classification SHALL use the Cabinet folder tree as taxonomy when available; oMLX receives metadata only (name, extension, size) — never file contents.
FR-7aWindows online launcher SHALL prefer system Python, then python-portable\, then one-time embeddable download. Offline launcher SHALL NOT require Python.

File Cards & Sorting

IDRequirement
FR-8Each file card SHALL display: original filename, file metadata (size, date, extension), AI suggestion badge with confidence, destination folder dropdown, rename field, and Accept/Skip/Override buttons.
FR-9Mandatory rename: a file SHALL NOT be staged until the user provides a renamed filename that differs from the original (enforced in UI).

Batch Staging

IDRequirement
FR-10Batch staging SHALL create a timestamped directory containing: a payload/ subfolder with copied files (renamed), a placement-manifest.json mapping each file to its destination, and a transfer-manifest.json with SHA-256 checksums.

Server Endpoints

IDRequirement
FR-11The Python server SHALL expose REST endpoints:
 
GET  /api/files             # List unsorted files
GET  /api/cabinet            # Cabinet tree
POST /api/classify           # AI classification
POST /api/stage              # Batch staging
GET  /api/config             # Read config
PUT  /api/config             # Write config
GET  /api/structure-rules    # Read structure rules
PUT  /api/structure-rules    # Write structure rules

PowerShell Engine

IDRequirement
FR-12The PowerShell engine SHALL support modes: verify, export, place, serve, all.
FR-13Verify mode SHALL check every file in a batch against its transfer-manifest.json (existence, size, SHA-256).
FR-14Place mode SHALL move verified files from the batch payload to their Cabinet destinations per placement-manifest.json.
FR-15Export mode SHALL walk the Cabinet tree and emit offline-structure-manifest.json (paths and counts only, no filenames).

Conflict Handling

IDRequirement
FR-16Conflict detection SHALL operate at three levels: folder conflict (destination folder does not exist), file conflict (destination file already exists), and no conflict.
FR-17Conflict resolution SHALL support: skip (leave file in batch), rename (auto-suffix), and overwrite (replace existing).

Receipts & Compatibility

IDRequirement
FR-18Placement receipts (placement-receipt.json) SHALL record the outcome of each file placement (placed, skipped, conflict-renamed, failed).
FR-19The v1 config format (archiveRoot, absolute inbox paths) SHALL be auto-migrated to v2 format (cabinetRoot, relative paths).
FR-20v1 manifests (transfer-manifest.json from v1 scripts) SHALL remain supported for backward compatibility.

UI & Structure Rules

IDRequirement
FR-21Structure rules SHALL be editable via the UI settings overlay and saved to structure-rules.yaml.
FR-22The UI SHALL display a summary status bar showing counts of pending, accepted, skipped, and conflict files.
FR-23The app SHALL support UNC paths (\\server\share) and drive-letter paths (D:\Archive) on Windows, and POSIX paths on Linux/macOS.

5. Non-Functional Requirements

IDRequirement
NF-1The entire UI SHALL be a single HTML file with embedded CSS and JavaScript — no external CDN, no npm, no build step.
NF-2The Python backend SHALL use only Python 3 standard library modules (exception: pyyaml for structure-rules parsing).
NF-3No cloud-based LLMs — classification uses only the local oMLX endpoint.
NF-4All paths SHALL be mount-agnostic: changing cabinetRoot in config is the only step needed when the Cabinet moves to a different drive letter or mount point.
NF-5File operations SHALL be atomic where possible — copy-then-verify, not move-then-hope.
NF-6The UI SHALL render correctly in Chrome 90+ and Edge 90+.
NF-7The Python server SHALL bind to localhost only (127.0.0.1) for security.
NF-8SHA-256 checksums SHALL be computed for every file in every batch.
NF-9The app SHALL handle files up to 4 GB individually.
NF-10Offline operations SHALL complete without any network access.

6. Constraints

IDConstraint
C-1Air gap is non-negotiable — the Cabinet machine has no internet access and will not gain it.
C-2No Python on the offline machine — PowerShell 5.1 is the only scripting runtime available.
C-3oMLX availability is not guaranteed — the AI classification must degrade gracefully to manual-only sorting.
C-4Browser sandbox prevents direct filesystem access — a local server (Python or PowerShell) is required for file operations.
C-5Two-phase prune contract: no source file is deleted until a verified receipt returns through the gate (BLU-1845).
C-6Folder names are taxonomy — the classification system is the Cabinet's folder hierarchy, not a separate database.

7. Out of Scope

IDItem
OS-1Automated USB scheduling or hotplug detection.
OS-2Full bidirectional replication or sync (this is one-way: online to offline Cabinet).
OS-3Cloud-based classification or any external API calls.
OS-4Mobile device support (tablet/phone UI).

8. Success Criteria

IDCriterion
SC-1A new unsorted file can be classified, renamed, and staged in under 30 seconds with AI assistance.
SC-2A batch of 50 files can be verified and placed offline in under 5 minutes.
SC-3Zero data loss — no file is deleted from source without a verified receipt.
SC-4The same HTML file works in both online and offline modes without modification.
SC-5Changing the Cabinet path (e.g., from D:\Archive to E:\Cabinet) requires only a config update, no code changes.
SC-6v1 configs and manifests are auto-migrated without user intervention.
SC-7The system works with oMLX unavailable, falling back to manual classification.

9. Acceptance Tests

IDTestExpected Result
T-1 Online Sort — Load 10 files in tosort/, classify with AI, accept all, stage batch. Batch folder created with payload/, placement-manifest.json, transfer-manifest.json.
T-2 Offline Verify — Copy batch to offline inbox, run verify mode. All files pass checksum verification, receipt generated.
T-3 Offline Place — Run place mode on verified batch. Files moved to correct Cabinet folders per placement-manifest.
T-4 Conflict: File Exists — Place a file where destination already has same-name file. Conflict detected, user prompted for skip/rename/overwrite.
T-5 Conflict: Folder Missing — Place a file to a folder that does not exist. Folder auto-created, file placed.
T-6 Round Trip — Full online sort, USB transfer, offline verify+place, return USB with receipt. Online side confirms placement, source files eligible for pruning.
T-7 UNC Paths — Set cabinetRoot to \\NAS\Archive, run export. Structure manifest generated correctly.
T-8 v1 Migration — Start with v1 config (archiveRoot, absolute paths). Auto-migrated to v2 format on first run.
T-9 Mandatory Rename — Try to stage a file without renaming. UI blocks staging, shows validation error.
T-10 oMLX Unavailable — Start online mode with oMLX endpoint down. UI shows “AI unavailable” badge, manual classification works normally.
T-11 Large File — Stage and verify a 2 GB file. SHA-256 computed correctly, file transferred intact.
T-12 Structure Rules Edit — Edit structure-rules.yaml via UI, re-classify a file. New rules reflected in AI suggestions.
T-13 Cabinet Path Change — Change cabinetRoot in config, restart. All operations use new path, no errors.
